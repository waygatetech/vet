Rulings (2026-10-08, Brian): --ticket <file>; findings JSON rendered by vet; map responses. New concept and contracts approved.

- `internal/config`: add `CriticCommand []string` (`critic_command`), defaulting to `[claude, -p]` when empty.
- `internal/critique`:
  - `Prompt(ticket, plan, concepts string, context []File) string`: instructs the critic to look for failure modes, missing or untestable acceptance criteria, overlap with existing concepts, and unstated contract changes, and to reply with only a findings JSON report (check = one of failure-mode | acceptance | overlap | contract).
  - `Run(ctx, argv, prompt) (findings.Report, error)`: runs argv via exec.CommandContext with the prompt on stdin. Tolerates a ```json fence around the reply. A command failure or invalid JSON returns an error (exit 3).
  - `Render(report) []byte`: writes the markdown with a `## C<n> [severity] check` heading per item.
  - `Check(critiqueMD, planMD []byte) ([]string, error)`: parses the C-IDs from the headings and `critique_responses` from the plan frontmatter, then returns the IDs that are unanswered.
- `main.go`: the `critique` subcommand. In normal mode it reads the plan, the ticket, `./concepts.yaml` and the `--context` files, runs the critic, and writes `<plan minus .md>.critique.md`. With `--check`, a missing critique file means exit 2; unanswered items are listed on stderr and exit 1.
- Tests: table tests for Check (all answered, missing, empty response, no items, no frontmatter), for Run using a fake command (`sh -c 'cat >/dev/null; echo ...'`) covering a good report, bad JSON and a nonzero exit, and the exit codes in main_test.go.
- concepts.yaml: register `critique`. README: usage and config.
